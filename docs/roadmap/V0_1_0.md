# Version 0.1.0

> **Navigation**: [Roadmap](./README.md) | [Documentation Root](../README.md)

The first working prototype: a daemon with two session lines that message and wake each
other, and an operator question queue. The tasks are ordered so that each depends only on
the ones before it. The task list is a proposal from the seeding session, and the
receiving line may revise it with the operator.

| # | Task | Done when | Status |
|---|---|---|---|
| 1 | Seed, plus a check of the seed against Appendix B | The package installs, gates are green, and the receiving line confirms nothing in the tracked files conflicts with Appendix B | Done 2026-10-25 |
| 2 | Data model and event log | Session lines, messages, wakes and operator questions are typed records in an append-only SQLite log, and a replay rebuilds the same state | Done 2026-10-25 |
| 3 | Daemon skeleton | `dromon start`, `dromon status` and `dromon stop` work against `dromond` over a Unix domain socket readable only by the user, with a versioned request format | Done 2026-10-25 |
| 4 | First engine adapter | One session line runs on Claude Opus 5.5, through a loop chosen with the operator, with the credential that loop permits, and the adapter probes and reports the engine's capabilities | Done 2026-10-25 |
| 5 | Layer 1 messaging and wakes | Two session lines exchange a message, and an idle recipient is woken by it | Done 2026-10-25 |
| 6 | Operator questions | A line asks through `ask_operator`, the question appears in `dromon questions`, `dromon answer` answers it, the answer wakes the line, and an open question survives a daemon restart | Done 2026-10-25 |
| 7 | Conversation control | A turn limit or budget stops a runaway exchange and raises an operator question | Done 2026-10-25 |
| 8 | Interactive client | `dromon attach LINE` opens an interface attached to one session line and its operator questions, several can be attached at once from different terminals, and a graphical interface can be launched from the client | Done 2026-10-25 |
| 9 | Per-project configuration | `.dromon/dromon.toml` defines the session lines, their engines and the wake policy, and an invalid file is rejected with a located message | Done 2026-10-25 |
| 10 | Continuous integration | Lint, type checks and tests run on Linux and macOS for Python 3.12 and the newest release | Done 2026-10-25 |

After the milestone, on the operator's direction on 2026-10-25, sandboxing reached
parity with Claude Code, as [`../protocol/SANDBOX.md`](../protocol/SANDBOX.md)
specifies, and engine settings reached parity with the settings in use in Claude Code,
Codex and Grok Build, as [`../protocol/SETTINGS.md`](../protocol/SETTINGS.md) specifies.
Drivers for GPT-6-Luna on Codex were then packaged, and a Codex adapter followed, as
[`../protocol/CODEX.md`](../protocol/CODEX.md) specifies. Dromon was then brought to the
point of being dogfooded in the epagoge project, with its local teacher model, as
[`../protocol/TEACHER.md`](../protocol/TEACHER.md) specifies. The terminal and
graphical clients were then taken near parity with Claude Code, Codex and Grok Build,
on a shared core, as [`../protocol/CLIENT.md`](../protocol/CLIENT.md) specifies and the
design records. Settings for lines and projects followed, changeable from a client as
overrides over the project file.

Out of scope for 0.1.0: communication layers 2 and 3, the stream processor model,
Keleusma policies through `pykeleusma`, a graphical client, teacher models and a PyPI
release. Publishing needs the operator's confirmation in session.
