Type: Added

- Every child start that takes two seconds or more is now recorded, written to the daemon's standard error and listed at the end of a test run, with where the time went, how long the start waited for the fork lock, how long it was in the call that forks, how many starts overlapped, and the load of the machine from `os.getloadavg` and, on Linux, the pressure stall figures of `/proc/pressure`. A test run writes each such line to the terminal at once, past pytest's capture, so a run that later hangs has already shown them.
- A stall report now says whether the call that forks has returned, which tells a thread stuck in `vfork` from one that waits for the program, and gives the same load figures and the processor time of each child, from `proc_taskinfo` on macOS and `stat` on Linux, with how many of its threads run. On macOS a child's state, which `libproc` reports as running for any process, is shown as `live`. An earlier reading of a stalled child as running was unfounded.
- `tests/test_spawn_stress.py` starts children from several threads at once by every path the daemon uses, with and without the fork lock, and measures the longest freeze of all threads. The counts come from the environment. 24,000 starts on macOS gave no stall either way, so the stress test did not reproduce it there, though a full gate run did once.
- A stall report on macOS also gives each child's resident size, page faults, pages read in, copy-on-write faults, Unix system calls and context switches, so a child that waits for memory shows as one. The first stall seen off continuous integration, in `tests/test_land.py` during a full sandbox gate on macOS, is recorded in the design document with what its report showed.
- A test that takes five seconds or more is named at once in the run's output, with the load of the machine, so a Linux run that is slow in one file and later killed by its timeout names the test. The design document records what four failing Linux logs show of two files that take minutes there and seconds elsewhere.
- Every call that forks is now timed where it passes, whoever made the start, and one of a second or more is recorded and written with the processor time the thread itself used in it, the size of the daemon, the steal time of a virtual machine and the throttling of the control group, which a log of a Linux run needs to tell a kernel that copies a large process from a machine that did not run it.
